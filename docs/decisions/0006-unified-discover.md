# ADR 0006: Unified Discover cache and provider boundaries

- **Status:** Accepted; F3 adds logical catalog reconciliation and local analytics in [ADR 0008](0008-unified-explorer-and-local-snapshots.md).
- **Context:** Discover must read metadata from local snapshots, Databricks DEV/PROD, and Purview without persisting credentials, scanning everything at startup, or treating metadata visibility as read access.
- **Decision:** Load each provider independently and lazily by hierarchy. Store returned metadata pages in SQLite WAL with separate contexts and TTLs (catalog 6h, schema 30m, table 15m, detail 1h; Purview assets 6h). Local snapshots are accepted only when their manifest and data file resolve inside the local datasets directory. Databricks `browse_only=true` means metadata-only, `false` is read-access evidence, and missing evidence means unknown. Purview uses the current Azure CLI identity against Unified Catalog Data Assets; no Atlas or alternate-identity fallback is attempted. Cross-environment table identity requires a known metastore and an exact physical path beneath a normalized logical catalog.
- **Consequences:** Provider failure does not erase successful cached pages; stale cached data is returned with an error marker when the provider context is known. The F3 UI shows one logical tree while the cache remains provider-scoped. Purview discovery now attempts ARM account discovery and checks delegated Unified Catalog API access; compatibility remains tenant dependent. Cache contexts are hashed; tokens and secrets are never persisted.
- **Evidence:** Databricks Unity Catalog list APIs expose pagination and `browse_only`; effective permissions can be inherited and are not queried per table. Microsoft Unified Catalog Data Assets is a preview API. The implementation therefore reports unknown when evidence is incomplete and records the API limitations in the UI and docs.
