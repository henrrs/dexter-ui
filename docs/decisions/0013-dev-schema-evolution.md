# ADR 0013: Direct schema evolution for DEV Delta tables

## Status

Accepted for F4.3.

## Context

F4.1 provides the canonical schema and deterministic comparison model. F4.2 has a schema editor for synthetic publication, but structural changes to an existing DEV table must work independently from synthetic data generation. Unity Catalog tables have logical names and environment-specific physical identities, and applying multiple DDL statements is not an atomic batch.

## Decision

- Keep canonical schema modeling and comparison in the existing F4.1 domain module. `SchemaDraft` stores an immutable baseline, stable field IDs, proposed field values, and explicit removed state. The ID is what distinguishes a user-requested rename from a drop plus add.
- Persist drafts by authenticated principal, workspace, DEV environment, and physical Unity Catalog table identity. Persist only metadata, plans, operation evidence, and generated SQL; never credentials or tokens.
- Regenerate plans in the backend from its stored draft. Browser input cannot choose SQL. The Databricks adapter quotes every identifier and string literal and accepts types through a restricted Spark SQL type validator.
- Keep Apply Schema Changes as the default direct `ALTER TABLE` strategy on the configured DEV workspace. It preserves table identity and records. PROD is denied in the API.
- Require existing Delta Column Mapping for DROP and RENAME, and existing Type Widening support for applicable type changes by default. The explicit Review flow may offer opt-in activation only when the selected DEV Warehouse, effective privileges, current table properties and protocol are verified as compatible. Activation uses the documented table property; Dexter never sets protocol version properties directly. Any unsupported, unverified, or potentially rewriting change remains blocked from this strategy. Adding NOT NULL without backfill is blocked. Setting NOT NULL is guarded by writer-protocol evidence and a read-only NULL count before any DDL; no changes are started if the count cannot be verified or is nonzero.
- Offer a separate, explicitly destructive Recreate DEV Table strategy from the same draft. It may drop only the verified existing physical DEV Delta table after the reused F4.2 safety assessment and a backend-checked confirmation bound to the reviewed plan/identity. Create a new empty table with the defined schema; never cast old records, stage or upload files, generate synthetic rows, or fall back to this strategy automatically. Managed and External storage types must match the source. External recreation uses a new authorized empty path and never deletes old files. A durable checkpoint is written before DROP; uncertain DROP/CREATE outcomes are reconciled from remote state and never blindly retried. Success requires a new table identity, equivalent schema/storage, and zero rows.
- Treat each DDL as an independently committed action. Save operation progress after each statement; re-read the remote schema after success or failure. If a command may have completed despite a failed response, preserve that uncertainty and require fresh review. Never claim rollback or retry old SQL automatically.
- Reuse the same editor from Table Workbench and Compare Tables. Keep synthetic generation and comparison as separate features; after validation, Compare Tables remains the existing way to inspect DEV against PROD.

## Consequences

The UX can propose edits offline after opening real DEV metadata and stores the draft in local SQLite. Apply requires an accessible DEV SQL Warehouse. Compatibility labels are contextual; column deletion and rename are breaking changes, and type widening/nullability require validation. Constraints visible in Unity Catalog are checked. Databricks does not expose a complete downstream dependency inventory through the current table detail read, so dependency analysis is not exhaustive and the UI must not imply that consumers have been checked.

The relevant Databricks behavior is documented in the primary sources: [column mapping for rename/drop](https://docs.databricks.com/aws/en/tables/features/column-mapping), [ALTER COLUMN syntax and type support](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-ddl-alter-table-manage-column), [NOT NULL constraints](https://docs.databricks.com/aws/en/tables/constraints), and [Delta type widening](https://docs.databricks.com/aws/en/tables/features/type-widening).

## Explicit empty-table recreation

The F4.3 recreation strategy reuses F4.2's read-only `assess_drop_recreate`, grant/lineage inspection, managed recovery evidence, External Location authorization, path-emptiness check, and no-retry DROP checkpoint. The publisher's synthetic generation and file upload stages are deliberately not used. DDL is generated from the same sanitized canonical schema draft and passed through the allowlisted Databricks type validator. The reviewed plan includes the exact fully qualified DEV name, storage type, selected External Location/new path, Warehouse, approved schema, and old physical table identity. The API requires an explicit confirmation boolean while revalidating the current profile, workspace, principal, baseline, table id, target fingerprint and stored plan immediately before queueing and again before DROP.

The adapter confirms that DROP left the target absent before CREATE. If the DROP response is lost but the table is confirmed absent, it proceeds with CREATE without resubmitting DROP. If CREATE returns an error or lost response, Dexter only inspects the table. A result is successful only when the physical ID changed, format/storage match, the final schema is equivalent, the External location matches when applicable, and `COUNT(*)` is zero. Otherwise the operation is recorded as partial/uncertain, metadata and table-list caches are invalidated, and the UI requires reconciliation. A verified replacement adopts a fresh draft baseline and clears the old-identity draft. An unexpected table or absent target remains locked for manual recovery; no DDL is replayed.

Managed data lifecycle follows the configured Unity Catalog recovery policy. External files at the old location remain untouched, and the new table is placed below a deterministic plan-specific child path of an authorized External Location after an emptiness check. Grants, ownership, unsupported properties, dependencies and consumers may change; visible lineage/grants and the limits of that evidence appear in Review. Unsupported constraints, policies, masks, properties, unknown grants, or unavailable lineage fail closed. The operation is registered in Operations Manager and cannot be cancelled after the destructive checkpoint.

## Explicit Delta capability activation

The 2026-11-08 refinement adds a deliberately narrow exception to the default requirement that features already be enabled. For an eligible DEV table, Review can inspect a selected SQL Warehouse and expose separate, unchecked choices to enable column mapping and/or type widening. The API re-reads table metadata and verifies the runtime/SQL version, effective MODIFY or owner permission, Delta properties, protocol versions and feature metadata before it allows Apply. A selected feature is part of the reviewed plan identity; changing the selection or Warehouse invalidates that review. PROD is rejected throughout.

The plan distinguishes `DIRECT_DDL`, `FEATURE_REQUIRED`, `REWRITE_REQUIRED`, and `UNSUPPORTED`. Only the first two can reach execution. Mapping activation and widening activation use allowlisted `SET TBLPROPERTIES` statements; protocol properties are never written directly. Before each structural ALTER, the worker observes the table again and compares it with the precise intermediate state expected from its own prior statement. It records the activation checkpoint, verifies the resulting property and protocol, and invalidates cached table metadata. This avoids treating an expected self-induced protocol update as external drift while still blocking unrelated concurrent changes.

Each statement is independently committed and may have an uncertain outcome. If activation or DDL fails after submission, the worker preserves the draft and partial evidence, marks reconciliation as required, and does not retry the mutation or claim rollback. The user must reconcile current physical metadata and submit a fresh review. There is no automatic rewrite path, table rebuild, REORG, VACUUM, or downstream consumer migration. Verification is conservative and based on the available Unity Catalog table metadata, the selected compute version and effective grants; it does not enumerate every external reader or prove its compatibility.

Capability behavior follows the official Databricks guidance: [column mapping](https://docs.databricks.com/aws/en/tables/features/column-mapping), [type widening](https://docs.databricks.com/aws/en/tables/features/type-widening), [feature compatibility and protocol management](https://docs.databricks.com/aws/en/tables/features/feature-compatibility), [SQL `current_version()`](https://docs.databricks.com/aws/en/sql/language-manual/functions/current_version), and [ALTER TABLE privileges](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-ddl-alter-table).

## Review/Apply state contract correction

The version 2 plan persists independent `physical_dev_baseline`, `proposed_dev_schema`, and advisory `reference_prod_schema` snapshots. Before DDL, the executor compares fresh physical DEV metadata to the reviewed physical baseline, then verifies the unchanged draft and only the capabilities required by its operations. The schema/capabilities observation comes from one fresh Unity Catalog table read. Schema semantics retain type aliases/precision/scale, identifiers, nullability, complex type ordering, constraints, defaults, generated/identity/mask metadata, partition indices and comments; top-level field order, transport positions and optional empty comments are normalized. Connection data, storage path representation and Warehouse state are excluded from capability fingerprints. Required unknown capability metadata blocks as unavailable, distinct from a confirmed change. Column mapping, widening, feature and NOT NULL protocol guards remain enforced.

The original false capability drift was caused by hashing the whole capability payload: Review replaced `storage_location` with a boolean while the worker hashed its original path. A failed pre-DDL attempt also triggered proposed-vs-physical validation in the UI, incorrectly presenting pending changes as execution mismatch. Pre-DDL failure now leaves baseline, desired edits and origins intact, with retry available. Plans using the old fingerprint contract require fresh Review; existing drafts migrate fingerprints without replacing metadata or origins.

After a completed or uncertain DDL, `/api/schema-evolution/reconcile` explicitly observes DEV and rebases remaining edits while preserving their provenance. Apply and Review remain blocked until reconciliation (or an explicit draft reset). The previous plan retains its original snapshots. A missing result from DROP/RENAME is never treated as proof of rollback or retried blindly. Schema Evolution still has per-process target serialization; it does not claim distributed DDL transactions or a lock against unrelated Databricks clients.

## Rejected alternatives

- Recreate as an implicit fallback for a direct change: rejected because it would silently discard records. Explicit recreation remains available as a separately reviewed, empty-table strategy.
- Automatically enable column mapping/type widening: rejected because the protocol and compatibility impact must be visible and explicitly selected by the user. The narrow Review option described above still requires verified compute, permissions, property and protocol evidence.
- Infer rename from a dropped and added field with a similar name/type: rejected because the evidence is ambiguous.
- Reuse the synthetic publication editor/runtime as the executor: rejected because existing-table evolution has different identity, concurrency, and partial-failure semantics.
