# ADR 0012: Synthetic generation plan and engine boundary

- **Status:** Accepted; F4.2 generation, Prepare DEV, and guarded Drop & Recreate are implemented. Reproducible dependency lock generation remains blocked in this checkout until the corporate npm and Python registries are configured.
- **Context:** Synthetic generation must be reusable by future Development Labs and must not couple domain rules to Databricks, HTTP, SQLite, or UI. Structured generation should remain bounded on a developer workstation.

## Decision

- Define `SyntheticGenerationPlan` and `ColumnRule` in the technology-neutral domain layer, using the F4.1 canonical schema. Serialize the plan, seed, locale, generator parameters, and publication intent; cap a run at one million records.
- Validate names, duplicate rules, generator/type support, nullability, null percentage, uniqueness, and enum/range parameters before generation. Unsupported complex schemas fail explicitly; there is no implicit conversion to STRING.
- Use DuckDB as the primary vectorized engine for structured values and Parquet output. Use Mimesis only for explicitly semantic columns. It must not process all rows/columns as a mandatory second pass.
- Generate Parquet incrementally. Advance one seeded Mimesis provider in stable row-major order for semantic fields so batch boundaries do not alter results and the provider's locale dataset is not loaded once per column. Store the generator/library versions and plan digest in a durable run manifest.
- Keep destination publication outside the generator. A bounded producer/consumer pipeline uses a one-item queue, a 128 MiB staging limit, two concurrent files, and serial 4 MiB Databricks SDK upload parts. Persist uploaded file size/checksum evidence before local cleanup so retries can resume from the manifest.
- Run generation in a separate worker process. Prefer cgroup v2 `MemoryMax=256M`; when unavailable, apply DuckDB's 64 MiB limit and a 220 MiB RSS guard at chunk/progress boundaries and report this as degraded protection, not as an equivalent hard ceiling.
- Revalidate source/destination identity, permissions, schema, and a review digest before publication. Limit writes to the explicitly selected DEV profile. Preserve existing schemas and external locations for Append/Replace, use run markers and idempotent staged files for retry recovery, and validate exact resulting schemas and row counts.
- Keep Drop & Recreate limited to unchanged, Dexter-provenanced experimental tables on the same DEV profile/workspace and physical table ID. Review visible dependencies/grants, owner or MANAGE authority, schema/constraints, row filters/masks, storage type, Delta history, and managed recovery policy before exposing the action. Unknown lineage, grants, storage, recovery policy, physical identity, or unsupported table properties fail closed; visible downstream dependencies are shown as impact warnings.
- Stage and validate all synthetic files before the destructive boundary. For External tables, choose a Unity Catalog External Location and a unique, empty child path; never reuse or delete old table files. For Managed tables, show the effective catalog/schema recovery retention before DROP. Bind review to a random review ID, workspace identity, target fingerprint, generated plan digest, and exact typed table name. Repeat preflight immediately before DROP, durably checkpoint the request, and disable automatic retry/cancellation after submission; uncertainty requires reconciliation. Recreate the approved schema, copy validated staging data, then verify schema and row count.
- Acquire a SQLite WAL lock keyed by DEV profile, workspace host, and exact table name in the same transaction as the destructive checkpoint. Keep it across worker restarts and all ambiguous states; clear it only after successful validation or a read-only reconciliation confirms the table is absent or the unchanged original survived. Never release the lock for a new/partially materialized table; that state needs administrator investigation.
- Preserve only explicitly supported safe table properties: validated Delta retention settings and Dexter provenance markers. Reject external URLs with query credentials/SAS or user-password credentials, and never put raw provider properties, credentials, or tokens into SQLite review/run manifests.
- The storage behavior follows the official Unity Catalog lifecycle: DROP removes External table metadata but leaves its files; Managed-table data follows the configured recovery retention (7 days by default, configurable). Unity Catalog `LIST` is used to verify the unique External destination is empty before DROP. Databricks lineage is treated as visible dependencies only, not a complete dependency graph.
- Pin Mimesis 22.2.0 alongside the already pinned DuckDB and PyArrow in `pyproject.toml`; `requirements.lock` is generated with hashes and `package-lock.json` is checked against `package.json`. `make setup`, `make lock`, and `make doctor` validate lock consistency. Lock resolution uses only the configured corporate registry and fails before contacting public registries if none is configured. API compatibility was exercised against Mimesis 22.2.0 for both supported locales after the user's explicit package-only pip install. In this checkout, corporate registry configuration is absent, so the generated Python hash lock and clean full-project installation remain uncertified; do not fabricate a lock from local package metadata.

## Consequences

The relevant platform behavior is documented by Databricks: [Unity Catalog object storage lifecycle](https://docs.databricks.com/aws/en/data-governance/unity-catalog/object-storage-lifecycle), [Managed versus External tables](https://docs.databricks.com/gcp/en/data-governance/unity-catalog/managed-versus-external), [LIST SQL](https://docs.databricks.com/gcp/en/sql/language-manual/sql-ref-syntax-aux-list), and [lineage system tables and limitations](https://docs.databricks.com/aws/en/admin/system-tables/lineage).

The plan and generator can be reused without Databricks. Preview and publication share the same deterministic generation implementation. Durable manifests and a bounded worker support restart recovery, while the UI keeps approval/review separate from execution. A fake-workspace suite validates adapter behavior; live workspace permissions, service-side SQL semantics, performance, and strict memory ceilings still require certification in a configured environment.
